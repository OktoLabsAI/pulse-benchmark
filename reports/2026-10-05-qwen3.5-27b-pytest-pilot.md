## Caveat, read first

Pulse's `ideation -> done` transition returns a server-side `500` on
ideations that have an architecture design attached — a live bug in the
current Pulse server, not something this run worked around by skipping the
gate. For all 10 staged tasks in this run, the architecture + mockup
resources were attached and **manually verified** (confirmed present via the
board UI, see the ideation-card screenshot in the raw evidence) rather than
carried through the automatic `ideation -> done` server transition used by
the earlier `qwen3.8-flash` run. The rest of the lifecycle (refinement, spec
derivation, FR/TR/AC fill-in, review/approve, implementation card) went
through the normal server-side gates unmodified.

Also: unlike the `qwen3.8-flash` pilot, this run's per-instance diff patches
and `predictions_direct.jsonl` / `predictions_staged.jsonl` were not
preserved as files in this repo — only the harness's own `report.json`
output per instance was kept. That's an open follow-up (see
[Next steps](../README.md#next-steps-in-priority-order)), not something
hidden: the raw reports are the actual evidence behind the numbers below,
not a summary of evidence that no longer exists.

## Why this result doesn't settle anything on its own

- **Same small-n caveats as the other two pilots apply.** 10 of 300 Lite
  instances, 1 of 12 repos — see the main
  [Caveats section](../README.md#caveats-read-before-quoting-any-number).
- **No discordant pair means no signal about which arm is "better" here.**
  A 10/10-vs-10/10 tie says staged didn't cost anything on this slice; it
  doesn't say staged helped, the way the one resolved gap in the
  `qwen3.8-flash` pilot did. Don't read this as "staged proven equivalent"
  either — n=10 both ways is too small to distinguish "truly tied" from
  "both arms happened to clear this particular slice."
- **The architecture-gate caveat above is load-bearing.** This run's staged
  arm did not go through the exact same server-enforced path as the
  `qwen3.8-flash` pilot's `ideation -> done` transition. Until the `500`
  bug is fixed and a run goes through the gate automatically, this result
  is evidence the *lifecycle content* (ideation, refinement, spec, task)
  produces working patches — not full evidence that every Pulse gate in
  the chain was exercised as designed.
- **No diffs preserved.** Unlike `qwen3.8-flash` and Qwen3.5-9B, this run's
  actual code changes aren't in this repo to inspect — only the harness's
  pass/fail verdict is. A reviewer can verify *that* the patches passed, not
  *how* staged and direct's patches differed (as the `pytest-6116` worked
  example does for the `qwen3.8-flash` pilot).

## Next steps

1. Fix (or get fixed) the `ideation -> done` `500` on ideations with an
   attached architecture design, then re-run the staged arm fully
   server-gated, no manual verification step.
2. Preserve per-instance diffs and `predictions_*.jsonl` for this model the
   same way the `qwen3.8-flash` and Qwen3.5-9B runs did, so a worked-example
   comparison (like `pytest-6116` in the `qwen3.8-flash` pilot) is possible.
3. Run a model where staged and direct are expected to diverge (e.g. repeat
   `qwen3.8-flash`-style instances known to separate the arms) to get a
   discordant pair under `Qwen3.5-27B`, rather than relying on a clean-sweep
   slice that can't show a staged advantage even if one exists.
